### 2.1 记忆账本 — 版本链存储与冲突检测（lib/ledger.ts）

核心设计：每条记忆不是 key-value，而是一个**版本链**（version chain），支持追溯变更历史。

```typescript
// 注入新记忆：精确匹配 → 模糊匹配 → 冲突检测 → 版本链写入
async injectClaim(options: InjectClaimOptions): Promise<LedgerEntry> {
  // 1. 精确查找 entity.attribute
  let existing = await this.storage.getByEntityAttribute(
    options.entity, options.attribute, this.teamId
  );

  // 2. 模糊查找 fallback（LLM 和 CLI 命名可能不一致）
  if (existing.length === 0) {
    existing = await this._fuzzyEntityLookup(options.entity, options.attribute);
  }

  // 3. 冲突检测：语义相似度 + 置信度差值
  const conflict = await this.detectConflict(newClaim, existing);

  // 4. 根据冲突类型自动路由：auto-cover / conflict-mark / human-confirm
  if (conflict) {
    return this._resolveConflictAndInject(conflict, options);
  }

  // 5. 无冲突：追加到现有版本链或创建新条目
  ...
}
```

冲突检测逻辑：

```typescript
// 基于语义相似度和置信度差值的三级冲突检测
async detectConflict(newClaim: LedgerClaim, existingEntries: LedgerEntry[]) {
  const similarity = semanticSimilarity(activeClaim.value, newClaim.value);
  const delta = Math.abs(newClaim.confidence - activeClaim.confidence);

  if (newClaim.confidence > 0.8 && activeClaim.confidence < 0.6) {
    type = "auto-cover";     // 高置信度自动覆盖低置信度
  } else if (similarity > 0.8 && delta > 0.15) {
    type = "auto-cover";     // 高度相似的细化更新
  } else if (delta < 0.15) {
    type = "conflict-mark";  // 置信度接近，标记冲突
  } else {
    type = "human-confirm";  // 需要人工裁决
  }
}
```

### 2.2 艾宾浩斯衰减模型（lib/decay.ts）

```typescript
// 记忆强度 = 2^(- elapsed / half_life)
// 不同类别的半衰期不同：decision/api=14d, process=7d, general=3d
export function calculateStrengthFromLedger(entry: LedgerEntry): number {
  const active = getActiveClaim(entry);
  if (!active || !active.valid_from) return 1.0;

  const elapsed = (Date.now() - new Date(active.valid_from).getTime()) / (1000 * 86400);
  const halfLife = entry.recall_half_life ?? 14;
  return Math.pow(2, -elapsed / halfLife); // S = 2^(-t/h)
}
```

## 3）项目亮点介绍

### 3.1 重新定义"记忆"：不是检索，是感知

传统 RAG / 知识库是被动式：你问了它才答。我们的系统是主动式：
- **不问也推**：系统主动告诉你"快忘了"（遗忘预警）
- **矛盾感知**：前后不一致时，主动推送等裁决（矛盾检测）
- **自动画像**：谁擅长什么，自动识别（TMS 专家画像）
- **AI 分析矛盾**：不仅标记冲突，还解释"谁在什么时候说了什么、哪个更可信、为什么"

类比人脑：你不会"搜索"自己记不记得——大脑会主动提醒你。

### 3.2 版本链存储：历史完整保留，永不覆盖

普通系统：v2 覆盖 v1，历史丢失。
我们的系统：v1 和 v2 同时存在，标记为 `conflicting`，等待人工裁决。
- 每个版本都有独立的置信度、时间戳、来源、确认人
- 裁决后 v1 标记为 `superseded`（不是删除），可随时回溯
- 版本链可视化，变更历史一目了然
- **AI 冲突分析**：LLM 自动生成时间线、确认人数对比、推荐裁决

### 3.3 艾宾浩斯遗忘曲线 + 类别感知半衰期 + 自适应学习

不是所有记忆遗忘速度都一样：
- **类别感知默认值**：decision=21天, api=14天, process=14天, security=7天, experience=30天, general=7天
- 记忆强度 = 2^(-elapsed / half_life)，低于阈值自动推送复习提醒
- **自适应学习**（v2.2 新增）：每次复习后，系统根据复习结果（有效/需更新）动态调整半衰期——稳定的记忆半衰期变长，易变的记忆半衰期缩短

### 3.4 工程可用性优先：LLM 波动不影响系统可用性

- LLM 提取是主路径，但不是唯一路径
- LLM 未能提取时，自动降级到手动 inject
- 手动 inject 支持 fuzzy lookup，即使 entity/attribute 命名不一致也能匹配
- 所有操作有降级路径，系统始终可用
- 向量搜索失败时，自动回退到关键词搜索

### 3.5 即插即用：接入成本 < 5 分钟

换一个新团队只需 3 步：
1. 安装 openclaw + team-memory-engine 插件
2. openclaw.json 里配 teamId（团队标识）
3. 绑定飞书群聊 WebSocket，自动监听

零定制代码，任何团队 5 分钟接入。

## 4）AI 亮点介绍

### 4.1 高阶 AI 技巧（v2.2 更新）

**LLM 驱动的自动记忆提取**

使用 `doubao-seed-2.0-pro` 模型，从飞书群聊中自动提取 entity.attribute.value 三元组，并自动完成：
- 闲聊过滤（午饭吃什么 → 不存储）
- 分类打标（decision / api / process / security / experience）
- 语义去重（相似内容合并）
- 来源追溯（谁在什么时候说的）

**语义相似度冲突检测**

注入新记忆时，不是简单的字符串匹配，而是用 Levenshtein 距离计算语义相似度，结合置信度差值进行三级冲突分类（auto-cover / conflict-mark / human-confirm），确保真正矛盾的内容不会被自动覆盖。

**AI 冲突解释**（v2.2 新增）

当检测到矛盾时，LLM 自动生成：
- 矛盾本质分析（为什么前后不一致）
- 完整时间线（谁在什么时候说了什么、几人确认）
- 推荐裁决（基于时间顺序、确认人数、置信度综合判断）
- 降级路径：LLM 不可用时，规则驱动的时间线对比 + 推荐

**向量语义搜索**（v2.2 新增）

- 调用 embedding API 为每条记忆和搜索查询生成向量
- 混合检索：60% embedding 相似度 + 40% 关键词得分
- LRU 缓存 500 条查询，避免重复调用
- 降级路径：API 失败时自动回退到关键词搜索

**AI 驱动的图谱依赖推理**（v2.2 新增）

- LLM 自动推断跨记忆之间的依赖关系（references, depends_on, contradicts, implements, updates）
- 填充 `dependency_graph` 字段，使知识图谱从纯规则转为 AI 推理
- 图中心性计算：识别结构性重要的记忆
- 冲突传播检测：一个矛盾可能影响哪些依赖记忆

**自适应衰减学习**（v2.2 新增）

- 类别感知默认半衰期：不同类型记忆遗忘速度不同
- 复习结果跟踪：每次 review 记录"有效/需更新"
- EMA 动态调整：基于复习历史，稳定的记忆半衰期变长，易变的缩短

**Fuzzy Entity Lookup**

解决 LLM 提取和 CLI inject 命名不一致的问题。exact match 失败时，用语义相似度做模糊查找：entity 相似度 >= 0.8 且 attribute 相似度 >= 0.7 时匹配成功。这是系统鲁棒性的关键设计。

### 4.2 人和 AI 的分工

| 环节 | AI 负责 | 人负责 |
|------|---------|--------|
| 记忆提取 | LLM 自动从对话中提取关键信息 | 无需人工干预 |
| 闲聊过滤 | 自动过滤，只沉淀有价值内容 | 无需人工干预 |
| 分类打标 | 自动分配 category 和 tags | 可选人工修正 |
| 冲突检测 | 自动发现矛盾，标记 conflicting | 人工裁决保留哪个版本 |
| 遗忘预警 | 主动推送到飞书，计算强度 | 点击"已复习"或"忽略" |
| 专家画像 | 自动分析谁贡献了什么领域 | 无需人工干预 |
| 知识图谱 | 自动构建实体关系网络 | 无需人工干预 |

**核心原则**：AI 负责"发现"（提取、检测、预警），人负责"裁决"（冲突解决、复习确认）。系统不替人做决定，只帮人做更好的决定。

**分工总览**：
> AI 负责（自动）：记忆提取 · 闲聊过滤 · 分类打标 · 冲突检测 · 遗忘计算 · 专家画像 · 图谱构建
> 人负责（决策）：冲突裁决 · 复习确认 · 忽略预警
> **AI 发现，人裁决；AI 算强度，人做决定**

### 4.3 核心模型选型思路

| 模型 | 用途 | 选型理由 |
|------|------|----------|
| doubao-seed-2.0-pro | LLM 记忆提取 | 中文理解能力强，推理深度足，适合从对话中提取结构化信息 |
| doubao-seed-2.0-pro | AI 冲突解释 | 分析时间线、确认人数、置信度，生成推荐裁决 |
| doubao-seed-2.0-pro | 图谱依赖推理 | 推断跨记忆之间的依赖关系，填充 dependency_graph |
| 备用模型（qwen/kimi/glm） | 降级路径 | 多模型容灾，doubao 不可用时自动切换 |
| embedding 模型 | 向量语义搜索 | 生成 dense vector，支持语义级检索 |

**设计哲学**：不依赖单一模型。系统核心（账本、衰减、风险、图谱）全部是确定性算法，LLM 只负责非确定性的"提取"、"分析"、"推理"环节。即使 LLM 完全不工作，系统依然可以通过手动 inject、规则冲突检测、关键词搜索运行。

### 4.4 AI 在系统中的深度分布（v2.2 更新）

| 子系统 | AI 深度 | 实现方式 |
|--------|---------|---------|
| LLM 记忆提取 | 100% AI | LLM 提取 + 闲聊过滤 + 分类打标 |
| AI 冲突解释 | 70% AI + 30% 规则 | LLM 生成分析，规则降级兜底 |
| 图谱依赖推理 | 80% AI + 20% 规则 | LLM 推断依赖关系，规则做中心性计算 |
| 向量语义搜索 | 60% embedding + 40% 关键词 | 混合检索，API 失败自动降级 |
| 自适应衰减 | 30% AI + 70% 算法 | 基于复习历史 EMA 调整，类别感知默认值 |
| 矛盾检测 | 40% AI + 60% 规则 | 语义相似度 + 置信度差值 |
| TMS 专家画像 | 纯算法 | 基于 category/tag 的贡献统计 |
| 遗忘计算 | 纯公式 | 艾宾浩斯 S = 2^(-Δt/h) |

### 4.4 引入 AI 后的工作流变革

**Before（没有 AI 记忆引擎）：**
1. 团队群里说了什么，靠人脑记
2. 有人离职/请假，知识断层
3. 新人来了，同样的问题问三遍
4. 前后矛盾的决定，没人记得
5. 找历史信息 = 翻群聊记录 + 问同事 = 5-30 分钟

**After（有 AI 记忆引擎）：**
1. 所有关键决策被 LLM 自动提取，沉淀到账本
2. 遗忘预警主动推送，防止知识断层
3. 矛盾更新自动检测，保留完整版本链
4. TMS 自动画像，新人来了知道该问谁
5. 搜索 = 即时返回 < 100ms

**量化改变**：
- 信息查找时间：从 ~2-30 分钟 → < 100ms（提效 83%-99%）
- 知识断层：从"人走茶凉" → "系统记住一切"
- 矛盾决策：从"没人记得上次说了什么" → "版本链完整保留"
