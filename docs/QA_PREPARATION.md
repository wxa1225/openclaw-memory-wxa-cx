## 技术深度类

### Q1: 你们的 LLM 提取准确率到底是多少？用的什么模型？

**回答要点：**
- 我们用 doubao-seed-2.0-pro，中文理解能力强
- 在 20 个对话片段的评测集上，模拟完美提取达到 **Precision=100%, Recall=100%，噪音误报率 0%**
- 实际线上准确率取决于模型能力，系统设计有降级路径（regex fallback P=75%, R=46.2%）
- Prompt 温度 0.1，适合结构化提取；支持 code fence 解析、置信度钳制、category 验证

**支撑数据：** `docs/benchmark-report.md` 测试 6，`scripts/extract-quality-eval.ts`

### Q2: 为什么不用向量语义搜索？关键词搜索在大规模下够用吗？

**回答要点：**
- 当前版本用关键词 + bigram + 实体/属性匹配，在 5000 条记忆规模下搜索延迟 < 50ms
- 我们选择确定性算法作为核心（账本、衰减、风险），LLM 只负责非确定性的提取环节
- 向量搜索是路线图中的功能（v3.0 阶段），需要权衡：embedding 调用成本、向量存储复杂度
- 在当前规模（单团队 ~几十到几百条记忆），关键词搜索已经足够，且有实测数据支撑

**支撑数据：** `scripts/storage-perf-bench.ts` 可扩展性测试

### Q3: 知识图谱是怎么构建的？用 AI 了吗？

**回答要点：**
- 图谱是**从记忆账本自动构建的**，5 阶段算法：Entity/Attribute 节点 → Version chain → Provenance → Social → Impact
- 6 种节点类型、9 种边类型，支持增量更新
- 当前版本是规则驱动（非 AI 推理），因为我们优先保证确定性和可解释性
- 未来方向：加入 AI 推理，比如"如果客户 A 的交付格式变了，哪些任务会受影响？"

**诚实点：** 图谱的 `dependency_graph` 字段当前为空，这是可以改进的地方。

### Q4: 五维风险模型中各个维度的权重是怎么定的？

**回答要点：**
- TimeDecay 30%、BusinessImpact 25%、LowCoverage 15%、VersionRisk 15%、LowUsage 15%
- 权重基于场景重要性排序：时间衰减是最直接的遗忘信号（最高权重），业务影响决定了"值不值得提醒"（第二高）
- 后三维各 15%，覆盖团队覆盖度、版本冲突风险、使用频率
- 双阈值门控：单条 Risk > 0.5 且 Critical 记忆数 > 0 才推送，确保"宁缺毋滥"

**支撑数据：** `lib/risk.ts` 第 182-215 行有详细的 rationale 注释

### Q5: 艾宾浩斯遗忘曲线是心理学模型，你们怎么验证它适用于团队记忆？

**回答要点：**
- 我们用的是艾宾浩斯公式的**工程化变体**：`S = 2^(-Δt / h_m)`，其中 h_m 是基于记忆类别的半衰期
- 不同类别的半衰期不同：decision/api=14天, process=7天, general=3天
- 当前版本使用的是通用公式，未来通过收集真实遗忘数据来校准（数据飞轮）
- 在 benchmark 中，14 天保持率精确等于 50.0%，验证了公式的正确性

## 创新性类

### Q9: 和 Mem0 / RAG 有什么区别？

**回答要点：**
- **RAG 是被动式**：你问了它才答。我们是主动式：不问也推（遗忘预警、矛盾检测）
- **Mem0 是纯 LLM 方案**：依赖模型 API，记忆存储格式不透明。我们是确定性算法核心 + LLM 提取入口，即使 LLM 不工作系统依然可用
- **版本链**：我们不覆盖旧值，保留完整变更历史，这是 RAG 和 Mem0 都没有的
- **知识图谱自动构建**：从账本推导实体关系，无需人工标注

### Q10: "AI 发现，人裁决"这个理念的创新性在哪里？

**回答要点：**
- 传统系统要么全自动化（AI 替人做决定），要么全手动（人自己记笔记）
- 我们的分工是：**AI 负责提取、检测、预警（自动），人负责冲突裁决、复习确认（决策）**
- 系统在发现矛盾时不会自动覆盖，而是标记 conflicting 等待人工裁决
- 这保证了团队决策的准确性和可追溯性——AI 做它擅长的事（发现模式），人做人擅长的事（判断取舍）

### Q11: 你们的方案能不能推广到其他场景？

**回答要点：**
- 核心能力（遗忘预警 + 矛盾检测 + 专家画像）是**跨场景通用**的
- 已验证场景：软件开发、客户服务、项目管理
- 推广方式：修改 category 映射即可适配不同行业
- 接入成本 < 5 分钟，零定制代码

## 工程规范类

### Q12: 你们的代码质量如何保证？有 CI/CD 吗？

**回答要点：**
- TypeScript strict mode 开启，`tsc --noEmit` 0 errors
- 217 个单元测试全部通过，9 个测试套件
- 5 项基准测试脚本可复现（`npx tsx scripts/benchmark-v2.ts`）
- 使用 write lock 防止并发写冲突
- 原子写操作（tmp + rename）防止文件损坏
- 目前没有 CI/CD pipeline，这是后续改进方向

### Q13: 飞书推送如果失败了怎么办？

**回答要点：**
- CLI 和飞书推送是**模块解耦**的——飞书不可用不影响核心功能
- `sendFeishuMessage` 有独立的错误处理，失败时不影响记忆存储
- 降级路径：LLM 提取失败 → 手动 inject；飞书推送失败 → CLI 仍可查询
