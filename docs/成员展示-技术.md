### 1. Fuzzy Entity Lookup — 解决 LLM 和 CLI 命名不一致问题

**问题**：LLM 提取时用 `客户A.交付格式`，CLI inject 用 `客户A.格式`，exact match 失败导致冲突检测失效。

```typescript
// lib/ledger.ts

async injectClaim(options: InjectClaimOptions): Promise<LedgerEntry> {
  // 1. 精确查找
  let existing = await this.storage.getByEntityAttribute(
    options.entity, options.attribute, this.teamId
  );

  // 2. Fuzzy fallback：exact match 失败时，用语义相似度做模糊查找
  if (existing.length === 0) {
    existing = await this._fuzzyEntityLookup(options.entity, options.attribute);
  }

  // 3. 冲突检测（现在能匹配到正确的条目了）
  const conflict = await this.detectConflict(newClaim, existing);
  ...
}

/** Fuzzy entity+attribute lookup when exact match fails.
 *  entity 相似度 >= 0.8 且 attribute 相似度 >= 0.7 时匹配 */
private async _fuzzyEntityLookup(
  entity: string,
  attribute: string
): Promise<LedgerEntry[]> {
  const allEntries = await this.storage.getAll(this.teamId);
  return allEntries.filter(entry => {
    const entityScore = semanticSimilarity(entity, entry.entity);
    const attrScore = semanticSimilarity(attribute, entry.attribute);
    return entityScore >= 0.8 && attrScore >= 0.7;
  });
}

/** Levenshtein-based semantic similarity */
function semanticSimilarity(a: string, b: string): number {
  if (a.includes(b) || b.includes(a)) return 0.7;
  const dp = levenshteinDistance(a.toLowerCase(), b.toLowerCase());
  return 1 - dp / Math.max(a.length, b.length);
}
```

### 2. 三级冲突检测 — 语义相似度 + 置信度差值

```typescript
// lib/ledger.ts

async detectConflict(
  newClaim: LedgerClaim,
  existingEntries: LedgerEntry[]
): Promise<ConflictResult | null> {
  const similarity = semanticSimilarity(activeClaim.value, newClaim.value);
  const delta = Math.abs(newClaim.confidence - activeClaim.confidence);

  // auto-cover: 高置信度覆盖低置信度，或高度相似的细化更新
  if (newClaim.confidence > 0.8 && activeClaim.confidence < 0.6) {
    type = "auto-cover";
  } else if (similarity > 0.8 && delta > 0.15) {
    type = "auto-cover";
  }
  // conflict-mark: 置信度接近，标记冲突
  else if (delta < 0.15) {
    type = "conflict-mark";
  }
  // human-confirm: 置信度差异大，需要人工裁决
  else {
    type = "human-confirm";
  }

  return { type, existingEntry, newClaim, confidenceDelta: delta, reason };
}
```

### 3. 飞书交互卡片 — 用户点击后实时更新版本状态

```typescript
// lib/card-action-handler.ts

export async function handleMemoryReviewAction(
  data: CardActionData,
  config: HandlerConfig
): Promise<CardActionResult | undefined> {
  const value = data.action?.value;
  if (!value || !value.action) return undefined;

  const ledger = new MemoryLedger(config.teamId, config.ledgerPath);
  const entry = await ledger.getEntry(value.memory_id);

  // "review" — 复习：重置衰减时钟
  if (value.action === "review") {
    await ledger.resolveConflict(conflict, { action: "confirm", ... });
    return {
      toast: { type: "success", content: "✅ 已复习 — 记忆强度重置为 100%" },
      card: buildUpdatedCard(entry, "review"), // 卡片变绿显示已复习
    };
  }

  // "update" — 保留新版本，旧版本 superseded
  if (value.action === "update") {
    await ledger.resolveConflict(conflict, { action: "update", ... });
    const updated = await ledger.getEntry(value.memory_id);
    return {
      toast: { type: "success", content: "已更新记忆" },
      card: updated ? buildUpdatedCard(updated, "update") : undefined,
    };
  }

  // "dismiss" — 保留旧版本，新版本 superseded
  // "confirm" — 两个都保留，都变为 active
  // "dismiss_warning" — 忽略遗忘预警
}
```

## 技术深度说明

### 设计决策 1：为什么用版本链而不是直接覆盖？

普通系统 v2 覆盖 v1，历史丢失。团队场景下，"客户A 交付格式从 PDF 改回 Markdown" 不等于"PDF 这个决定从未发生过"。版本链保留了完整的决策历史，支持后续审计和回溯。

### 设计决策 2：为什么 fuzzy lookup 是必要的？

LLM 提取是自由命名（entity/attribute 由 LLM 决定），CLI inject 是规则提取（regex 固定命名）。如果没有 fuzzy lookup，同一个"客户A的交付格式"可能被 LLM 存为 `客户A.交付格式`，CLI inject 用 `客户A.格式`，永远匹配不到，冲突检测形同虚设。

### 设计决策 3：为什么飞书卡片要实时更新？

用户点击按钮后，卡片必须给出视觉反馈，否则用户不知道操作是否成功。我们通过 `updateCardFeishu()` 调用飞书 PATCH API 实时更新卡片内容（绿色=已复习，版本状态更新=已裁决），而不是仅靠 toast 通知。
